# Signed, scanned and recipient-encrypted exchange

A signature answers “did the selected partner key sign these bytes?” A malware scan asks a different question about the same immutable bytes. Both checks must pass before an operator releases the file. An approved workflow can then encrypt that released revision for a pinned recipient and send it to a pinned receiver. Each decision uses ordinary permissions, policy, immutable revisions and retry receipts; inference stays disabled.

This selected assisted profile combines the existing mechanisms through real interfaces: authenticated HTTPS intake, detached OpenPGP verification, genuine ClamAV, CSV validation, separate release, an approved recipient-encrypted SFTP workflow, independently retrieved/decrypted bytes, and a signed audit snapshot. It uses synthetic data and local resources. Production installation, independent operators, broader peers and the complete baseline remain unqualified.

## Operator sequence

Use the documented [OpenPGP intake](openpgp.md), [scanner enrollment](scanners.md), [CSV policy](intake.md) and [encrypted delivery](encrypted-delivery.md) commands with actual enrollment output. Do not copy qualification UUIDs, fingerprints or timestamps into a deployment.

1. Authenticate the sender with its scoped identity. Obtain the complete signer and recipient fingerprints through a trusted channel. Enroll public keys for their separate verification/encryption purposes; private partner signing and recipient decryption keys remain with their owners.
2. Enroll the exact local scanner configuration and observed engine/database version. Select both that scanner reference and the signer reference in the same CSV intake policy. Required order is signature verification, scan, CSV validation, then an explicit release decision.
3. Upload the file into durable hold using its actual length/digest and an operation key. Attach its exact detached signature to the held revision using the file digest, policy hash and current check revision. Missing signatures do not spend a scan attempt.
4. Run the check and inspect its report. It binds the same source digest to the signature proof, scanner/profile/version/configuration and CSV outcome. A pass still leaves the file held. Release requires the exact file, policy and report hashes and revision; changed authority or context cannot silently select another revision.
5. Register the receiver's host identity, destination directory and credential references. Review the typed workflow's exact source, destination, recipient key and encryption profile, then approve that immutable workflow revision. Preview reports intended effects without contacting the receiver.
6. Start the approved run against the released file. The worker first prepares and durably records an exact ciphertext artifact under the normal custody quota and worker fences. Retrying after a receiver outage uses that retained artifact. It does not silently generate a different ciphertext for the same frozen intent.
7. Inspect the actual delivery observation. In this profile it records remote ciphertext length/digest, host identity and file-fsync acknowledgment. Remote directory durability across power loss is not established, and business acceptance is `unknown`. A receiver import needs its own contract and receipt; this file-transfer observation does not promise one.
8. Retrieve the ciphertext independently with stock SFTP. Compare its digest to the recorded ciphertext, decrypt with the recipient's own GnuPG, compare the plaintext to the original source, and independently verify the original detached signature.
9. Export an authorized audit snapshot and verify it with an independently trusted audit public key and stock OpenSSL. Follow the source, report, release, workflow run, ciphertext and delivery event references. The snapshot authenticates those exported records; prior database tampering, protected retention and downstream consumption remain separate boundaries.

Only protected SSH-client and audit-signing references enter the application runtime for their existing operations. Raw credentials and private keys never enter prompts or model context. The independent GnuPG fixture's private signing/decryption keys stay outside the application container. Audit records contain bounded metadata and hashes, not source file contents or raw detached signatures.

## Selected qualification

`python3 scripts/qualify-scanner-real.py --runtime-reference .private/EXACT_RUNTIME/state.json --combined-peer-reference .private/FRESH_SIGNED_FIXTURE/manifest.json --combined-marker-reference .private/FRESH_SIGNED_MARKER_FIXTURE/manifest.json` retains every original real-scanner assertion and then runs the combined exchange. Select both protected fixture references explicitly. They must be fresh, digest-verified native GnuPG fixtures; their existing signature-age policy is unchanged.

The actual Linux/amd64 application runs under emulation on this arm64 Mac. Scanner, application, stock curl and a test relay share the owner-authorized hard **4 GiB memory/one CPU** cgroup. PostgreSQL and the small native receiver/crypto observers are separate existing resources; no global machine cap is claimed. The scanner uses the pinned official ClamAV 1.5.4 image and read-only daily 28168/main 63/bytecode 339 databases. Both generations' kernel observations are retained across the exact task-container restart.

The current development transfer client accepts numeric loopback destinations. The fixture uses a loopback socat listener with four children and a 30-second inactivity limit to carry opaque SSH bytes to the separate native stock OpenSSH receiver. The product still validates the real receiver's host key end to end. This relay is a test network fixture; it does not qualify a production gateway, arbitrary remote destinations or scanner TCP access. The scanner continues to use its protected Unix socket.

The successful exchange includes a receiver outage, retained ciphertext, actual container/application/scanner restart and original-key recovery. It checks that the exact original ciphertext reaches the independently retrieved/decrypted result. A wrong signature is rejected while the real scanner is paused, proving it cannot wait for or bypass signature validation. A separately valid signature over the harmless EICAR marker passes signature verification but is rejected by the real scanner before CSV parsing or delivery. A valid signature cannot certify safe content.

[Qualification evidence](qualification/evidence/F024-signed-scanned-exchange.json) records exact source and artifact hashes, fixture/observer limits, the signed audit verification, original harness failure and remaining work. The original F023 scanner cases retain their original evidence. Ordinary foundation checks do not start the real scanner. The exact task runtime is stopped on success or failure; protected data, models, PostgreSQL and retained evidence are preserved.
