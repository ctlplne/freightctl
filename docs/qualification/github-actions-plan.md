# GitHub Actions qualification plan

Updated 2026-11-02. This plan moves reproducible work from the owner's shared ARM Mac to short-lived GitHub runners. It covers the existing public `ctlplne/freightctl` repository. A green job proves only the named test on the recorded commit, operating system, architecture, and peer. It does not close a parity row, whole customer journey, release gate, or independent adoption claim by itself.

## Operating rules

1. Run source, dependency, unit, race, fuzz and safe synthetic stand-in tests on pull requests and `main`. A pull request is untrusted code: use `pull_request`, a read-only token, no repository secrets, no privileged follow-up workflow and no persistent checkout credentials. Each job owns a fresh runner and its own loopback PostgreSQL, SFTP, browser or cryptographic peer.
2. Check `uname` or the native Windows platform before claiming an architecture. Cross-compilation checks packaging only. Pin actions and tool versions; record actual runner image, tool/peer versions and image digests in the job output or a reviewed safe manifest. A mutable runner label alone is not a version record.
3. Keep raw payloads, keys, tokens, model prompts, scanner databases and full native logs in ignored runner paths. Public Actions logs may contain only bounded, reviewed diagnostics. Runner files disappear after the job. `ci-qualification-summary.py` now provides an allowlisted state/commit/hash/command-count/output-closure/cleanup summary for the next stock-peer matrix run; native peer/browser versions stay in provisioning logs. Five refusal/privacy contracts pass, but its first GitHub execution remains pending. Never print the raw manifest or its command arguments. Do not upload raw artifacts, publish images/packages, push from CI, or deploy from these workflows. A safe checked-in qualification record links the commit and Actions run and states its limits.
4. Fail a gate when a prerequisite, protected sandbox, peer, assertion, resource cap or evidence closure fails. Preserve the first failure. Do not mark a skipped or conditional job green for an untested capability. Re-run the original journey after a fix.
5. Keep local inference off. No GitHub job downloads weights, loads a model or calls an inference endpoint until the owner authorizes a named endpoint, disclosure policy and explicit compute allowance. A parser fuzz test for untrusted model output is not inference qualification.
6. Real malware scanning may use only an isolated task-owned scanner capped at **4 GiB RAM and one CPU**, including the standard signature database. It has no model permission. The existing F026 aggregate replay remains manual because the owner deferred it.

The repository contract currently commits directly to local `main`; GitHub therefore tests the pushed commit after it arrives. These jobs are visible regression gates, not a pre-push merge barrier. CI never authors commits, so `imfeelingtheagi <288773099+imfeelingtheagi@users.noreply.github.com>` remains the verified author and committer for local changes. Required branch checks would need a separately approved branch/review workflow change.

Use only [standard GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). GitHub documents them as free and unlimited for public repositories; larger runners have separate charges. Per-job timeouts and one-process Go/Node settings keep the plan bounded even when the runner VM has more capacity. Keep all durable private evidence and production credentials outside this public CI path.

## Sequence for changing CI

1. Keep run 11's native Linux and stock-peer results bound to commit `1ebf6d0`. Diagnose the first Windows failures under D103, retaining the permission/durability assertions. Keep per-architecture results separate.
2. Promote portable existing scripts in small groups. For each: write the runner provisioning command, platform/peer assertion, resource and time bound, safe evidence reference, failure cleanup and exact acceptance claim. Run it once on GitHub and retain the first failed log before changing the script.
3. Repair Windows native behavior, then add real scanner and packaging jobs. Keep scanning and packaging apart from the fast pull-request path until their fresh-runner dependencies and output safety pass; move them to `main` or a scheduled/manual cadence with explicit red state. Do not use `continue-on-error` to call them qualified.
4. Before any protected external peer or real model job, define a named environment and obtain the missing authority. An untrusted pull request never receives credentials or production network access.
5. Review this table whenever the product adds a protocol, importer, workflow type, release artifact or supported platform. Update the parity/journey ledgers only from the corresponding actual-environment evidence. Keep assisted deployment, independent operator adoption and enterprise qualification as separate reports.

The immediate plan is deliberately tied to existing executable scripts. New names in a workflow do not create a capability. Where a script cannot run on an ephemeral runner, the gap stays explicit until a real adapter and a live run exist.
