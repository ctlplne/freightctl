# GitHub Actions qualification plan

Updated 2026-11-02. This plan moves reproducible work from the owner's shared ARM Mac to short-lived GitHub runners. It covers the existing public `ctlplne/freightctl` repository. A green job proves only the named test on the recorded commit, operating system, architecture, and peer. It does not close a parity row, whole customer journey, release gate, or independent adoption claim by itself.

## Operating rules

1. Run source, dependency, unit, race, fuzz and safe synthetic stand-in tests on pull requests and `main`. A pull request is untrusted code: use `pull_request`, a read-only token, no repository secrets, no privileged follow-up workflow and no persistent checkout credentials. Each job owns a fresh runner and its own loopback PostgreSQL, SFTP, browser or cryptographic peer.
2. Check `uname` or the native Windows platform before claiming an architecture. Cross-compilation checks packaging only. Pin actions and tool versions; record actual runner image, tool/peer versions and image digests in the job output or a reviewed safe manifest. A mutable runner label alone is not a version record.
3. Keep raw payloads, keys, tokens, model prompts, scanner databases and full native logs in ignored runner paths. Public Actions logs may contain only bounded, reviewed diagnostics. Runner files disappear after the job. `ci-qualification-summary.py` now provides an allowlisted state/commit/hash/command-count/output-closure/cleanup summary for each stock-peer matrix run; native peer/browser versions stay in provisioning logs. Seven refusal/privacy contracts and the native collection/arrival/schedule and original-routing summaries pass on candidate `cdbe5e2`; both routing summaries pass. Never print the raw manifest or its command arguments. Do not upload raw artifacts, publish images/packages, push from CI, or deploy from these workflows. A safe checked-in qualification record links the commit and Actions run and states its limits.
4. Fail a gate when a prerequisite, protected sandbox, peer, assertion, resource cap or evidence closure fails. Preserve the first failure. Do not mark a skipped or conditional job green for an untested capability. Re-run the original journey after a fix.
5. Keep local inference off. No GitHub job downloads weights, loads a model or calls an inference endpoint until the owner authorizes a named endpoint, disclosure policy and explicit compute allowance. A parser fuzz test for untrusted model output is not inference qualification.
6. Real malware scanning may use only an isolated task-owned scanner capped at **4 GiB RAM and one CPU**, including the standard signature database. It has no model permission. The existing F026 aggregate replay remains manual because the owner deferred it.

The repository contract currently commits directly to local `main`; GitHub therefore tests the pushed commit after it arrives. These jobs are visible regression gates, not a pre-push merge barrier. CI never authors commits, so `imfeelingtheagi <288773099+imfeelingtheagi@users.noreply.github.com>` remains the verified author and committer for local changes. Required branch checks would need a separately approved branch/review workflow change.

The native-platform workflow runs automatically when application sources, embedded browser inputs, Go dependencies, checkout-byte policy or that workflow change; it also offers manual dispatch. Changes confined to qualification scripts or prose do not consume another Windows/Mac unit run. Such an omitted run is not a pass for the new commit: retain the last tested candidate and exact application-source scope. The Linux stock-peer matrix still runs the changed qualification scripts against real services.

The layout separates [native Linux/race/PostgreSQL/fuzz](../../.github/workflows/native-linux.yml) from [stock-peer journeys](../../.github/workflows/stock-peers.yml) and [source checks](../../.github/workflows/core-checks.yml). It preserves the runtime job bodies exactly. Linux native triggers include Go/application/browser inputs, dependency files, PostgreSQL/GnuPG provisioning scripts and its own workflow; stock-peer triggers additionally include all qualification scripts. This avoids repeatedly queueing unchanged native application tests during browser-fixture diagnosis. The stock-peer path filter also excludes changes confined to Go `_test.go` files under `cmd/` or `internal/`: Go omits these files from server builds, while native Go/PostgreSQL jobs still execute the changed tests. Application Go/SQL, browser/dependency, provisioning/qualification-script and own-workflow changes remain included; manual dispatch can replay any candidate. The exclusion uses GitHub's ordered [negative path patterns](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore). A filtered-out stock run is no new runtime evidence. The split source job and stock collection/arrival/schedule/original-routing jobs pass on `cdbe5e2`; its Linux integration matrix and eight fuzz targets also pass; the corrected-revision job also passes. Mac ARM unit/race passes again; Windows remains red at D103.

Use only [standard GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). GitHub documents them as free and unlimited for public repositories; larger runners have separate charges. Per-job timeouts and one-process Go/Node settings keep the plan bounded even when the runner VM has more capacity. Keep all durable private evidence and production credentials outside this public CI path.

### Gates beyond a standard hosted runner

[GitHub's hosted runner limits](https://docs.github.com/en/actions/reference/limits) cap a job at six hours. Its [standard public Linux specification](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) provides four CPUs, 16 GB memory and 14 GB SSD. Those limits constrain these GOAL.md claims:

| Goal requirement | What Actions can do | What still needs a named environment |
| --- | --- | --- |
| 72-hour mixed-workload endurance | Start, observe and collect safe checkpoints from a continuous external run. | One continuously running estate with durable evidence, enough disk and the approved scanner/model profiles. Chaining fresh six-hour VMs is a different failure model. |
| 100 GiB resumable and 1 TiB streaming correctness | Run bounded smaller protocol/stream checks and orchestrate a large external test. Generated streaming data can reduce fixture disk needs, but does not prove 100 GiB resume persistence. | Adequate source/custody/receiver storage, independent digests, actual interruption/restart and connector limits. A standard 14 GB runner cannot retain the required resume estate. |
| Reference 8-vCPU throughput and scale | Detect regressions on the observed hosted VM and run correctness under bounded load. | The specified reference hardware, receiver/network/storage and exact workload; four hosted CPUs cannot be relabeled as the eight-CPU performance reference. |
| Multi-host HA, network partitions and restore | Orchestrate separate permitted hosts and gather safe evidence. Same-host containers remain useful fault-contract fixtures. | Real independent failure domains, backup/key/storage ownership and controlled network faults. One hosted runner cannot establish multi-host availability. |

Queue time and execution time are recorded separately. A queued, canceled or timed-out job provides no runtime pass; GitHub capacity delay is not permission to emulate an untested architecture on the owner's Mac. No larger paid runner or external infrastructure is provisioned by this plan without owner authority.

## Sequence for changing CI

1. Keep run 11's native Linux and stock-peer results bound to commit `1ebf6d0`. Diagnose the first Windows failures under D103, retaining the permission/durability assertions. Keep per-architecture results separate.
2. Promote portable existing scripts in small groups. For each: write the runner provisioning command, platform/peer assertion, resource and time bound, safe evidence reference, failure cleanup and exact acceptance claim. Run it once on GitHub and retain the first failed log before changing the script.
3. Repair Windows native behavior, then add real scanner and packaging jobs. Keep scanning and packaging apart from the fast pull-request path until their fresh-runner dependencies and output safety pass; move them to `main` or a scheduled/manual cadence with explicit red state. Do not use `continue-on-error` to call them qualified.
4. Before any protected external peer or real model job, define a named environment and obtain the missing authority. An untrusted pull request never receives credentials or production network access.
5. Review this table whenever the product adds a protocol, importer, workflow type, release artifact or supported platform. Update the parity/journey ledgers only from the corresponding actual-environment evidence. Keep assisted deployment, independent operator adoption and enterprise qualification as separate reports.
