# FTPS channel binding boundary

Status: cryptographic component verified; the later receiving adapter has native service/CLI evidence and awaits native stock-client qualification. See [the receiving profile](../ftps.md).

FTP uses one connection for commands and another for file bytes. Two people behind the same router can have the same public IP address. Checking that address does not prove that a file connection belongs to the person who signed in. RFC4217 discusses this data-connection hijack problem in [section15.1.2](https://www.rfc-editor.org/rfc/rfc4217.html#section-15.1.2) and [section15.2.6](https://www.rfc-editor.org/rfc/rfc4217.html#section-15.2.6). The following is freightctl's strict TLS1.3 profile, not a claim that RFC4217 mandates this exact implementation.

`internal/crypto/ftps.go` gives each accepted control connection its own random TLS ticket key. Its data connections must resume a TLS1.3 session with that key. A ticket from another control connection fails, even with the same certificate and IP address. The adapter constructs one binding per accepted control connection; sharing a binding between clients would break the boundary. The [Go TLS documentation](https://pkg.go.dev/crypto/tls#Config.SetSessionTicketKeys) describes the library's ticket-key mechanism; Go1.26.10 remains the pinned application toolchain.

Successful application authentication and its audit commit must precede `AllowData`. A TLS ticket alone grants no account or file permissions. The adapter must retain the authenticated tenant/partner/credential revision, reauthorize every operation through custody, and reject a second login on the same control session. Control handshakes are fresh; a resumed data session cannot become a new control connection. Closing the binding permanently refuses later handshakes. The adapter must also cancel custody contexts and close already established streams; `Close` is not a network or account revocation mechanism by itself.

Certificates are bounded regular files without symlinks or group/world write access. Private keys use the existing protected, bounded secret reader. PEM buffers and temporary ticket-key buffers are cleared. Go's TLS parser and ticket implementation retain their own key objects; clearing caller buffers cannot erase those library-owned copies. The server must bound connection count, lifetime and retained identity objects. This component does not establish HSM custody or validated cryptographic compliance.

Actual native ARM tests use certificate-verified loopback TCP/TLS, process real post-handshake tickets, and check same-session resumption, missing/foreign tickets, authentication, shutdown, control/data role separation, trust, hostname, TLS version and protected-file refusals. These are tests of the cryptographic boundary. Stock FTPS interoperability, explicit/implicit command sequencing, byte persistence, interruption, resume, passive/active handling and gateway operation still require their own evidence.

## Protocol-engine selection finding

The original reviewed candidate [ftpserverlib v0.32.7](https://github.com/fclairamb/ftpserverlib/tree/v0.32.7), commit `a4adf0322c6c4f72e027f5106eeb918d5086f58f`, has a useful `FileTransferError` callback before cleanup close on detected transfer errors. Its [passive-listener implementation](https://github.com/fclairamb/ftpserverlib/blob/v0.32.7/transfer_pasv.go) binds `:0`, or `0.0.0.0` for a configured port range. `WrapPassiveListener` runs after the socket has opened, and the transfer retains the original listener as its deadline setter. Closing/replacing that socket in the wrapper cannot supply a correct listener/deadline lifecycle and also opens the wildcard socket first. At F057 that unpatched candidate remained only in ignored cache. The later product dependency below is an explicitly patched, pinned copy.

The receiving adapter now uses an auditable MIT-licensed pinned copy under `third_party/ftpserverlib`, with original/local file hashes and preserved upstream tests. Its explicit passive IP is validated before listening; port multiplexing is unavailable with that setting. Refusal-only command policy and active-socket wrappers let the adapter enforce TLS sequencing, numeric same-peer/unprivileged active destinations and cancellation. Numeric PORT/EPRT parsing does no DNS work, and EPRT accepts RFC2428 delimiters with matching address families. A socket EOF without TLS close notification remains an error instead of becoming apparent completion. Upstream test identities are generated at runtime instead of committing reusable private keys.

Native ARM service and public CLI journeys exercise both TLS modes, passive/active sockets, opaque bytes, text mode, append/REST, namespace operations and interruption/foreign-ticket refusals against actual PostgreSQL/storage. They use an explicitly resumed Python TLS client stand-in. The Mac's curl/LibreSSL pairing remains refused because it does not resume the control ticket for data. The native GitHub stock-client and full engine gates remain pending. Receiving rows are implementing; sending rows remain planned. No whole FTPS row or customer journey is qualified.
