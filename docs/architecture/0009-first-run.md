# One-time local installation enrollment

First-run enrollment is a deployment-administrator command. Ordinary serving processes never receive that connection or new tenant/partner/credential write grants. There is no public bootstrap endpoint and no implicit network trust in a workspace JSON file.

The operator prepares an exclusive, directory-synced mode-0400 plan before changing PostgreSQL. The plan binds generated tenant/partner/admin/request UUIDs, three bounded NFC labels, the exact administrator grants, a credential SHA-256 and an existing durable custody identity. Credential files stay protected and are never embedded in a plan, event or result. Preparing a plan does not establish an installed tenant or a qualified exchange.

Applying it requires the separately configured deployment-admin role with explicit superuser/BYPASSRLS maintenance authority. The migrator's advisory lock serializes schema changes; exclusive table locks serialize first-run enrollment with other setup attempts and legacy enrollment. All installed migration checksums and forced domain row policies must match. Setup reads the immutable singleton receipt first: an exact normalized request returns its original result. Otherwise any tenant/partner/account refuses initialization. A new setup atomically inserts its hierarchy, first credential, immutable event and exact result receipt. The database guard joins the receipt to the identity and event. A receipt failure rolls back the entire hierarchy.

Migration 17 adds one forced-RLS relation, `installation_enrollments`, with tenant, partner and initial-actor scope. The runtime receives SELECT only, with no bootstrap write or role membership. Existing migrations, grants, accounts and file state are preserved. Ordinary account management remains the shared authenticated browser/API/CLI path after enrollment. Replaying setup never resurrects a revoked credential or invalidated session; its result is historical enrollment evidence.

The browser reference importer accepts at most 16 KiB and extracts only versioned tenant/partner UUIDs. It does not select an origin, read a referenced host file, trust advertised grants or run instructions. Explicit credential selection and normal same-origin session admission still decide access. A stale file can therefore fill stale IDs but cannot grant authority.

The current exercise uses an empty disposable database on a retained task-owned PostgreSQL instance, real storage, Chromium, stock curl and an explicit loopback TLS identity. It is assisted same-host evidence. A production installer/offline bundle, general tenant/partner lifecycle, invitations/providers, delegated trust/activation, audited emergency access, native platforms and independent operator adoption remain required.
