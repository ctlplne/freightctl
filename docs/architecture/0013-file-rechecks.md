# 0013: approved re-checks create linked checked revisions

The original accepted file, check binding, report, signature, release proof and queued transfer meanings remain immutable. Re-checking creates a new checked revision containing exactly the source bytes, with durable lineage to that source and a newly selected current policy. It never labels the old receipt as newly scanned or redirects an old queued job.

A root administrator who currently has read, write, intake management, check-run and check-release permissions can preview a plan for their own source. The plan freezes source digest/length/event, original check revision/state/report and signature references, old/new policy references and hashes, current storage/root/authority and a conditional namespace target. Review loads both immutable policy definitions and verifies their hashes. A live old check worker prevents a plan; an expired reservation remains historical and cannot complete. The new policy must retain any required signature/scanner control. Signature reuse is explicit and binds an exact retained artifact and unchanged selected signer reference; otherwise a new signature is required.

Saving the immutable plan reserves new file/signature identities but performs no byte access. A separate hash/revision approval rechecks source, policy, current keys/scanner configuration, authority and namespace selectors. Cancellation is terminal. Copy is another explicit operation. It rechecks all bindings and creates a held revision, with no check verdict and no publication.

The copy uses two separate PostgreSQL admission slots, the existing custody byte/entry quota lock, a 60-second operation context and bounded authenticated reads. It holds a PostgreSQL transaction/row lock across bounded local filesystem I/O; it makes no network/model call. This operation therefore uses transaction ownership rather than a separately committed worker lease. Other protocol/scan/delivery leases and retry budgets remain unchanged. A dead connection cannot commit a completion; fixed intent-owned object identities and non-overwriting staging prevent a late copy from changing another revision.

Bytes and any explicitly reused signature are synced before one transaction commits file acceptance, normal held check/signature bindings, lineage completion and the original-key receipt. After uncertain commit, replay returns that receipt. After rollback/death, only the exact approved intent's object may be adopted after size/digest/mode checks. Three fixed staging-slot pairs are reserved in the approved definition. A partial intent-owned object is retained in place; a retry may use another reserved pair. Complete objects can be adopted only after hash, mode and persistence checks. Exhausted slots need cancellation and a new reviewed request. No object is published, overwritten or silently deleted. Ordinary reconciliation remains read-only and never adopts arbitrary orphan bytes. Host filesystem calls that never return still need host/storage recovery.

The resulting file uses ordinary signature attachment, fresh checks and separately reviewed release. A conditional target swap occurs only on that later release. Original failed/detected/expired revisions keep their meanings and availability rules. Copy does not waive a detection, manufacture a clean result or grant downstream business acceptance. Policies that remove a required signature/scanner need a different future exception mechanism and are refused here.

Migration 21 adds actor-private forced-RLS intent and immutable staging-slot relations with immutable definition/effect identities, event-bound transitions, source/policy/control and derived-acceptance guards. Existing migrations, check/release guards and permission sets remain unchanged. Private plan payloads are redacted from ordinary event/audit feeds while their bounded state/hash references remain visible. Application and real interface qualification must establish these claims; this architecture document alone establishes none.
