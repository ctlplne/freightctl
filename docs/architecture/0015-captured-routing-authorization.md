# Changing routing for a captured batch

F041 is in progress. This decision describes the implementation and qualification contract; code presence does not qualify the feature.

A captured batch can have no complete decision under its original routing rules. Editing a workflow must not change that job or reinterpret an existing run. Add a separate, versioned routing authorization for the exact captured job. It uses the ordinary workflow definition, compiler, file policies, delivery intents, consent, workers and receipts.

The authorization names an already approved schema-2 revision in the same workflow family. Its source configuration must exactly match the original collection, including the connection revision, manifest contract, target directory and byte limits. Both the original capture authority and the target workflow must remain current. Manual and scheduled collections retain their original execution cutoff; scheduled collections additionally retain their original occurrence and calendar checks. This authorization neither extends a cutoff nor repairs revoked capture authority.

Before proposing or approving it, every newly owned input must be durably captured, available under ordinary intake and still published at its exact path. None may have a run or a recorded local disposition. An authorization cannot recall bytes or reinterpret queued, attempted, uncertain or completed work. Unchanged inputs owned by an earlier job remain with that job.

The immutable definition binds the original job ID/revision/hash, producer manifest hash, original and target workflow references, current actor authority, storage identity and namespace root. An ordered list binds each newly owned input ID, file ID and exact compiled plan hash. At most 64 entries fit within the existing definition budget. Plans are inspected one input at a time rather than returning an unbounded aggregate response. Go and PostgreSQL independently derive the original facts and recompute every plan binding.

Proposal does not change routing. Approval is a distinct `workflow_approve` decision on the exact definition hash and record revision. It atomically makes that authorization the effective choice for future admission. The definition also binds the prior effective decision, so an intervening approval or revocation makes a stale proposal fail. A proposed record can be withdrawn without changing the effective choice. Revoking an approved choice stops its unfinished work; it does not fall back silently to older rules. Before any run exists, a later separately reviewed authorization may replace that decision.

Ordinary batch admission still validates every pending sibling before useful partial queue admission. Each new run stores the exact routing-authorization ID, target workflow and immutable plan. SQL refuses the original workflow as a fallback once an effective routing decision exists, and independently checks the selected plan against its authorized input binding. Queue capacity can delay work without changing choices. Workers recheck the exact authorization along with all existing source, workflow, account, connection, key, intake and dispatch guards. Historical runs keep their original meaning.

Authorization rows are actor-private under forced RLS. Their events and generic command receipts are redacted in ordinary feeds and audit exports, while the protected journal retains the original payload. Read-only preview cannot write an authorization, create a run, reserve capacity, open bytes or contact a peer. Browser, API and CLI share the same typed proposal, approval, revocation and withdrawal operations, idempotent keys and private status/history.

Qualification must include the original blocked batch, a reviewed corrected workflow, actual stock-source capture and independent receivers, whole-sibling intake, separate consent per selected file/step, explicit local results, no recontact or resend of unchanged input, partial capacity, original-key response loss, restart/reload, concurrent admission/approval, stale prior decisions, revoked source/calendar/target/actor authority, forged facts/plan bindings, foreign scopes and feed/audit privacy. Use real PostgreSQL and custody, preserve the first failures and source/output epochs, and restore exact task resources. No model or scanner starts; F026's aggregate remains owner-deferred. All full product requirements remain open until separately proven.
