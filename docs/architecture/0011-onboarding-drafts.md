# Partner onboarding draft versions

Requirements are untrusted data. A contact's responsibility is not an account role, and a protocol or receipt choice is not an executable destination or verified result. This increment stores the first part of the onboarding journey while keeping testing, approval and activation explicitly separate and unfinished.

Migration 19 adds `onboarding_plans` and actor-private `onboarding_commands`, bringing the forced-RLS domain relation count to 41. Both are append-only. The non-owner runtime gains SELECT/INSERT only; no new elevated writer role or credential grant is introduced. SQL policies require the current tenant/partner and a live root credential carrying `admin` and `accounts_manage`. A tenant directory grant does not cross this boundary.

The existing partner account-management advisory lock is taken before authentication/session locks for writes. This serializes writes with account security changes and other plan edits without reversing lock order. The service validates a strict bounded typed definition, checks current authority, and checks a prior operation receipt before deciding whether to create anything. New writes must match the frozen authority and previous plan version. Exact replay still requires current authority but returns its original historical result; it cannot restore authority or create a new version.

One transaction inserts the immutable `OnboardingPlanRecorded` event, its contiguous version projection, `OnboardingCommandCompleted` event and exact private receipt. Trigger guards bind the projection and receipt to their source events, author, scope, definition, version and time. A late receipt failure rolls back the events and projection. The service hashes canonical Go JSON; reads validate and rehash stored definitions before disclosure. Explicit tenant/partner predicates support indexed queries in addition to forced row policies.

The browser freezes the full typed command and one operation key. It independently hashes Go-compatible canonical JSON and validates response joins before confirming success. Ordinary definitive refusals require a new review; a lost response retries the original frozen command. Contact text renders as ordinary text. Unknown response fields cannot become command authority. The API/CLI reject unknown or duplicate command fields, including endpoints and invented activation/approval fields.

Contact and free-form requirements remain in the protected journal, not ordinary audit payloads. `Events` and `SnapshotEvents` redact only the two new event kinds to a marker plus original-payload hash. Snapshot byte admission still counts the original payload before redaction. Current account-management authority is required for direct plan reads, and original-actor authority for receipt replay. This does not provide contact erasure, protected external retention or a journal rebuild implementation.

Document limits bound parsing and review, not edition capacity: 64 contacts, 64 requirements and 24 KiB canonical definition per draft, with paginated lists. Existing 21 account grants are unchanged. No inference, scanner engine or new background service is needed.

Real PostgreSQL tests cover version/replay concurrency, rollback, source-event guards, forced-RLS privacy, current/historical reads and rotated authority. Native browser and stock curl add first-partner draft review, response loss, concurrent edits, revocation/restoration, audit redaction and restart. Full J05 still requires tested credential/connection/folder bindings, independent exchange evidence, exact approval, activation and queued-work key lifecycle.
