# freightctl

freightctl is a ctlplne product for secure, automated file exchange between partners, customers and internal systems. It is being built as a broad, free, self-hosted core with private AI assistance for workflow creation, migration and operations.

The product target is complete paid-incumbent workflow parity, followed by measured improvements in migration, operator effort, security and operating cost. The repository contains the execution contract, qualification records and an incomplete local custody implementation. No production capability or complete customer journey is qualified.

Start with [GOAL.md](GOAL.md), [AGENTS.md](AGENTS.md), and [STATUS.md](STATUS.md).

For the implemented local first tenant, partner and administrator path, see [first-run enrollment](docs/first-run.md). It includes protected setup plans, exact retry and browser sign-in; production installation and complete journeys remain unqualified.

For explicit tenant directory authority and ordinary browser/API/CLI enrollment of another partner, see [partner enrollment](docs/partner-enrollment.md). Complete partner onboarding and production activation remain required work.

For versioned partner contacts and exchange requirements with reviewed saves and private retry receipts, see [onboarding drafts](docs/partner-onboarding.md). Saved requirements remain drafts until the required testing, approval and activation mechanisms are implemented and qualified.

For recorded read-only SFTP tests of an exact saved requirement and registered receiver, see [onboarding connectivity](docs/onboarding-connectivity.md). Connectivity evidence remains separate from a file exchange and production approval.

For required scans, exact release and the selected real ClamAV runtime evidence, see [local scanning](docs/scanners.md). The scanner stays unloaded between explicit qualification runs; local inference remains off.

For the selected combined signed-file, genuine scanner, separate release and recipient-encrypted exchange with independent receiver/audit verification, see [signed/scanned exchange](docs/signed-scanned-exchange.md). Full customer journeys remain open.

For selected read-only recovery of original SFTP receipt evidence after trust rotation, see [receipt observations](docs/receipt-observations.md). [F035](docs/qualification/evidence/F035-independent-production-approvals.json) adds independent named-account production review and preserves every browser summary after correcting the original F033/F034 evidence gaps. See [independent approvals](docs/independent-approvals.md). The full verification replay remains pending at the owner’s request.

For an administrator rule requiring named-account consent for each exact outbound SFTP file across direct CLI, ordinary workflow, onboarding test and production paths, see [dispatch approvals](docs/outbound-dispatch-approvals.md). Configuration release approval and file dispatch approval are separate, cumulative checks.

For reviewed calendars, bounded published-file selection and restartable ordered outbound workflows, see [scheduled workflows](docs/scheduled-workflows.md). Activation, queueing and execution are separate decisions; ordinary file and dispatch approvals still apply.

For explicit read-only remote inputs with ready manifests, whole-batch custody, intake gates and separate downstream decisions, see [collection workflows](docs/collection-workflows.md). Repeated input claims remain bound to their original workflow revision; scheduled remote admission and full J03 remain open.
